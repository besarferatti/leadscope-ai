# Credit wallet staging checklist

New subscriptions use the existing EUR 6,900-cent monthly PRO price in `STRIPE_PRO_MONTHLY`. In staging, use an equivalent test price. Top-ups are priced in USD. Keep the legacy price IDs for subscription status sync. Existing Stripe subscriptions, orders, and historical counters are retained. Active legacy Stripe customers keep included access while their subscription remains active.

1. Start from a disposable staging database. Keep the canonical Stripe migration and apply the migration history in order. Four historical Stripe duplicates keep their version numbers and are now no-ops. The public audit migration now creates its previously manual prerequisite if missing. Apply the profile authorization migration from PR #121 before the credit wallet migration.
2. Configure the Stripe test webhook for `invoice.paid` or `invoice.payment_succeeded`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `checkout.session.completed`, and `checkout.session.async_payment_succeeded`. The Supabase webhook endpoint must accept Stripe's signed requests without a Supabase JWT.
3. Set `STRIPE_MANAGE_ONLY_PORTAL_CONFIG` to an active staging portal configuration with subscription updates disabled. Enable cancellation, invoice history, and payment method updates as appropriate. The application rejects portal configurations that allow plan switches.
4. Verify a new PRO Checkout, a renewal, and a current paid PRO account from before the wallet. The Billing page's **Refresh wallet** button reconciles the current paid cycle for existing PRO customers. Replay the paid invoice and confirm the grant remains 7,400 credits. Verify that a stale invoice cannot add spendable credits after its period ends.
5. Run each of the four test-mode top-ups and replay its Checkout events. Verify that each grants once, appears in order history, and has no expiry. Confirm monthly credits are spent first, including when one debit spans both pools.
6. Verify that legacy Checkout prices are rejected and legacy subscription history is still visible. Confirm that two simultaneous actions competing for a balance sufficient for only one produce a single debit and one insufficient-credit response.

The configured price is charged once per started provider attempt, including attempts without results. An automatic discovery retry starts a new attempt. Stripe refunds and disputes require manual wallet reconciliation before production rollout.

For a support correction, open **Admin → Users → Add credits**, confirm the recipient, and enter the amount and an internal reason. Manual credits never expire and are used after monthly credits. The wallet records the administrator and reason privately. The recipient sees an **Admin credit** entry. Retrying the same request cannot grant it twice.

Local PostgreSQL 18.6 rehearsal passed all 33 migrations using fixtures for Supabase Auth and Storage. Two separate database sessions competed for a balance that could cover only one action. One debit succeeded, the other waited for the lock and returned insufficient credits, and the final balance was zero.

In a temporary Stripe Sandbox, the application created and completed the €69 PRO Checkout and all four USD top-up Checkouts. The application webhook handler verified signed copies of the test events, including `invoice.payment_succeeded`, against a local wallet database. Replaying the events did not duplicate credits. The temporary sandbox key did not permit Stripe Test Clocks, so the real renewal and delivery to the hosted Supabase webhook still need staging verification.
